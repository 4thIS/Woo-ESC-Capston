## 3. 결정별 근거

### 3.1 D1 — 폰트 글자 집합: KS X 1001 2,350자

**쟁점 (2026-09-21, P2 서브셋을 전제로 정리, P1을 택하면 아래 2~5·7·9~11은 사라진다)**

1. **글자 집합을 어떻게 정하나** — e-fairboard 방식(코퍼스 빈도 상위 2,000자, 도메인 무관)과 사용자 제안(예상 과목·특강명 기반, 교수명·예약 문구는 예측 어려움)을 절충해 **KS X 1001 2,350자를 안전망으로, 실데이터를 하한선으로** 쓴다. 글자 하나 추가 비용은 **172B**(20px 60B + 28px 112B). `[계산]`
2. **화면 글자의 입력 경로가 3곳이다** `[확인]`: CSV 임포트(`server/app/domain/csv_import.py:117-120`)·REST 스키마(`server/app/schemas.py:59-70` `_bytes_max`)는 **UTF-8 바이트 길이만** 검증하고 글자 종류는 안 본다. 예약(`Reservation.subject/professor`)은 자유 입력이라 예측이 가장 어렵다. 글자 집합 검증을 넣을 지점은 CSV 임포트·REST 스키마 두 곳(wj 영역).
3. **집합 밖 글자 처리** — (가) 입력 거부 (나) 경고 후 저장 (다) 렌더 폴백(□/공백). 입력·오류 메시지는 wj·mh, 렌더 폴백은 dh.
4. **글자 집합의 단일 진실원** — 폰트 생성(dh)과 서버 검증(wj)이 같은 목록을 써야 한다. 위치 후보: `lora_proto/`(cw 전담·lockstep) / 펌웨어 쪽에 두고 서버가 복사(드리프트 위험) / 공용 자산 폴더. **cw 결정 필요 → D6.**
5. **갱신 경로** — 새 글자가 필요해지면 폰트 재생성 + 펌웨어 재배포가 필요하다. OTA 경로 유무 `[미검증]` — 그래서 초기 집합을 넉넉히 잡는 게 안전.
6. **집합 크기 N별 저장량**(한글 N자+ASCII 95자, 1비트) `[계산]`:
   - 2,000자: 20px 125,700B + 28px 234,640B = 360,340B
   - **2,350자(KS X 1001, 채택)**: 20px 146,700B + 28px 273,840B = 420,540B
   - 3,000자: 532,340B / 4,000자: 704,340B / 전체 11,172자: 1,937,924B
   - 실데이터 300자(아래 15) + ASCII·기호 100자: 68,800B — N 후보가 아니라 **반드시 포함해야 하는 하한선**
7. **저장 형식과 훅** — 커밋 훅이 500KB 초과 파일을 막는다. hex `.h`는 바이너리의 6.33배라 20px 4.28MB로 걸린다. **`.bin` 형식이면 420,540B로 훅을 그대로 통과**한다.
8. **글자 조회 방식** — 서브셋은 코드포인트→글리프 위치 조회(이진탐색/표)가 필요하다. 전체 한글의 산술 인덱스(`cp - 0xAC00 + 95`, v1 방식)보다 코드가 늘어난다.
9. **협의 순서** — wj(검증 추가), cw(단일 진실원 위치), mh(입력 오류 메시지). dh-04 마감(3주차)과 맞물려 자산 생성(Task 3) 전에 정해져야 한다.
10. **실데이터 확보 — 완료(2026-09-22)**. 글자 빈도 요약본 3종(과목명 233자·교수명 107자·한글 외 문자 33종)을 받아 분석. **범위 고지: 이 데이터는 한 학과의 학생 계정으로 접근 가능한 범위 안에서 얻은 최대치다. 다른 학과·전체 학사 범위를 대표하지 않는다.** 과목명의 22%(52/233자)·교수명의 15%(16/107자)가 표본에서 1회만 등장해, 범위를 넓히면 새 글자가 계속 나올 걸로 보인다 `[추정]` — 그래서 실데이터만으로 집합을 정하지 않고 KS X 1001을 안전망으로 썼다.
11. **커버리지 자동 검증(제안)** — 픽스처·CSV 표본의 모든 글자가 집합에 있는지 테스트로 확인할 수 있다. ⚠️ 승인 필요
12. **P1로의 후퇴 경로** — 생성 스크립트를 글자 집합 파라미터화해 두면 실데이터 조사 결과가 나쁘거나 플래시가 남으면 전체 한글로 재생성만 하면 된다.
13. **한글 외 문자도 집합에 필요하다** — 화면 스펙이 `·`(푸터)·`–`(강의시간)·`↑`/`↓`(목록)를 쓴다. v1 폰트 생성은 ASCII+한글 음절만 굽고 그 밖 문자는 안 그린다(`KoreanFont.h`의 `ngIdx`가 -1 반환). **실측(2026-09-22)**: 받은 한글 외 문자 33종(로마숫자·중점·하이픈·영문·숫자·괄호·전각 등)에 `–`·`↑`·`↓`는 **없었다** — 우리 UI가 그리는 기호라 학사 데이터엔 원래 안 나온다. 이 3개는 실데이터와 별도로 반드시 추가.
14. **실데이터 취급 — 완료(2026-09-22)**. 원본이 아니라 글자·코드포인트별 빈도 요약본 3개(CSV)를 받았다. 원본(교수 이름 등)은 저장소에 없고 수집한 쪽 로컬에만 있다.
15. **최종 글자 집합 분석(2026-09-22)** `[계산]`: 과목명 233자 + 교수명 107자(겹치는 56자 제외) = 284자. **놓칠 뻔한 것**: 상태 보조 문구·요일·layout 8 안내문 등 우리 쪽 고정 한글 UI 카피(폰트로 그려지는 것만, 라벨류 이미지는 제외)도 필요 — 서로 다른 55자 중 **16자(`끝납느늘단더되말않았없에요월입휴`)는 과목/교수 데이터에 없어서 284자만 썼으면 빠뜨렸을 것**. 최종 합집합 **300자**, 전부 KS X 1001·2,000자 빈도 목록 안. 표본 한계(10번)로 300자만 쓰는 건 위험 → **N = KS X 1001 2,350자**로 최종 확정.

**축 A(글자 범위) 선택지 비교**
- **전체 한글**: 누락 없음, 인덱스 산술이라 단순(v1 그대로). 단점: 크다(§5 P1 참조).
- **서브셋 2,000자(e-fairboard 방식)**: 0.36MB, 훅 통과. 단점: 목록 밖 글자 빈칸, wj 입력 검증 필요. 흔한 성씨·이름 약 130자(자체 표본) 전부 포함했으나 표본이 약함. KS X 1001 2,350자 중 359자가 목록에 없음(예: 잚·잦·짬).
- **KS X 1001 2,350자(채택)**: 실데이터 300자를 전부 포함하는 것을 실측 확인(15번). "희귀 글자 없음"을 가정이 아니라 근거로 말할 수 있는 유일한 안.

**최종 확정(2026-09-28, 이슈 #34)**
- 쟁점 4(단일 진실원)는 **`lora_proto/`로 결정**됐다. cw가 PR #64로 `lora_proto/lora_proto/charset.txt`(생성기 `tools/gen_charset.py`, 드리프트 테스트 포함)를 머지했다. 폰트 생성(dh)은 이 파일을 순서대로 읽고, 서버 입력 검증(wj)은 `lora_proto.charset.unsupported()`를 쓴다.

- 한글 외 추가 글자는 14자로 확정됐다: 로마 숫자 `Ⅰ`~`Ⅹ` 10자(다른 학과의 `Ⅲ`·`Ⅴ`를 대비해 표본에 나온 3자에서 넓힘) + `·` `–` `↑` `↓`. 합계 **2,459자**. `[확인]` `charset.txt` 데이터 줄 수
- 전각 `Ａ` `Ｉ`는 목록에 넣지 않는다. 서버가 입력을 받을 때 전각 ASCII를 반각으로, 가운뎃점 변형을 `·`로 정규화한다(계약 ⑤, wj 몫).
- `–`(U+2013)는 KS X 1001에 없으므로, 폰트 생성은 cp949가 아니라 유니코드 코드포인트로 글리프를 뽑는다. `[확인]` cp949 인코딩 실패로 확인

### 3.2 D2 — 저장소 반입: (d) 빌드타임 생성

D1이 P2'(420,540B)로 정해지며 `.bin` 자체가 이미 훅(500KB) 아래라, 애초 고려하던 (a) 훅 예외·(b) 500KB 분할·(c) Git LFS는 불필요해졌다. 남은 쟁점은 "이 `.bin`을 펌웨어 컴파일에 어떻게 넣느냐"였다.

**제약**: 로컬에 `espressif32` 플랫폼이 설치돼 있지 않다(`pio platform list` — `native @ 1.2.1`뿐, `[확인]`). `[env:terminal]`(실기)은 아직 없다. 실기 전용 메커니즘은 문서(`[출처]`)까지만 확인 가능하다.

1. **`board_build.embed_files`(PlatformIO 공식, espressif32 전용)** `[출처]` docs.platformio.org — objcopy로 `extern const uint8_t X_start[]/X_end[]` 심벌을 만든다. `embed_txtfiles`는 널 종단이 붙어 0x00 바이트가 실데이터인 폰트에 부적합 — `embed_files`를 써야 한다. **알려진 함정**: platform-espressif32 이슈#425, 일부 버전에서 링크 목록에 안 들어가는 버그 보고 `[출처]`. `native`에서는 이 옵션이 의미 없어(objcopy 기반은 espressif32/Arduino 전용) 로컬 실측 불가.
2. **(d) 빌드타임 생성 — 실측 완료** `[확인]`: `extra_scripts = pre:<script>.py`로 빌드 직전에 `.bin`을 읽어 `const uint8_t[]` 배열 `.cpp`/`.h`를 생성. 스파이크로 직접 검증(생성 후 삭제, `git status` clean·`pio test -e native` 31/31 회귀 없음 재확인):
   - `lib/<생성폴더>/`에 쓰면 LDF가 자동 링크(S3 plan Task 3의 "`lib/`는 자동 링크" 규칙과 동일). `build_src_filter` 수정 불필요.
   - 0x00 바이트가 안 잘리고 보존됨을 테스트로 확인(`SPIKE_FONT_DATA[5000..5003] == 0x00,0x00,0xff,0xff`).
   - 원본 `.bin`을 바꾸고 재빌드하면 즉시 갱신(스테일 캐시 없음, 5,004B→10B로 확인).
   - `pio check -e native`가 생성 파일도 스캔하지만 5KB 샘플 기준 새 지적 0건(Total 67 유지). 420KB 실제 규모의 소요시간은 `[미검증]`.
   - **실제 도입 시 필요**: 생성물이 `lib/` 밑에 생기므로 `.gitignore`에 추가해야 한다 — 안 하면 untracked로 잡혀 실수 커밋 위험(스파이크에서 실제로 잡히는 것 확인).
   - 호스트·실기 양쪽에 같은 메커니즘을 쓸 수 있어 보인다(`extra_scripts`는 플랫폼 무관 빌드 훅). 실기 쪽 실동작은 `[미검증]`.

- **색 버전을 두 벌 만들지 않는다.** 1비트 마스크 하나를 `Adafruit_GFX::drawBitmap(..., color)`로 원하는 색에 찍는다. v1 `main.cpp`도 같은 방식이다. 스펙 "필요한 자산"의 "RED용 흰 글자·BLACK용 검정 버전이 각각 필요"는 마스크 하나로 충족된다.
- **칩 이미지는 글자 마스크만 담는다.** 칩의 검은 바탕 사각형과 패딩은 렌더 코드(Task 4)가 그린다. 자간(+0.04em)은 이미지에 구웠다.
- **라벨(과목명·담당교수·강의시간)은 이미지로 굽지 않는다.** 20px/400 폰트로 그린다. 글자는 전부 `nanum20r`에 있고, 폭(57·76·76px)이 라벨 칸 104px에 들어간다. `[확인]` 스펙 자산 표는 "v1 라벨 이미지 재사용"이지만, v1 라벨은 `stroke_width=1`을 준 가짜 볼드(`generate_images.py:144`)라 스펙 타이포그래피(20/400)와 맞지 않았다. 화면 결과가 스펙과 같아 스펙 변경은 필요 없다고 본다.
- **78px `설정 대기`는 만들지 않는다.** layout 8은 상태 띠를 그리지 않고, 제목은 타입표에서 62/800이다(`terminal-epaper.md:47`, `:73`, `:187`). 처음에 만들었다가 쓸 곳이 없어 뺐다.
- 각 이미지는 w·h·bytesPerRow·baseline(이미지 윗변 → 베이스라인)을 갖는다. baseline은 `BitmapFont::baseline`과 같은 규약이라, 크기가 다른 요소를 같은 베이스라인에 맞출 수 있다(`firmware/lib/bitmap_image/bitmap_image.h`).

### 3.8 Task H — 자산 전체를 흑백 힌트 렌더로 다시 굽기 (2026-09-30, ⚠️ 팀 승인 필요)

첫 PNG를 보고 "같은 글자 안에서 어떤 획은 옆 획보다 두껍다"는 문제가 제기돼 원인을 쟀다.

**원인** `[확인]`
- 생성기는 Pillow 안티에일리어싱으로 그린 뒤 임계값 128로 잘랐다. 이 방식에서는 FreeType이 가로 방향 힌트를 쓰지 않아, 세로 획이 1px/2px(20px Regular), 2px/3px(20px Bold)로 섞인다. 힌트를 끈 렌더와 분포가 같다(58.6/35.6% vs 58.7/34.8%).
- 나눔고딕 400·700·800 TTF에는 TrueType 힌트(`fpgm`·`prep`·`cvt`)가 있고, 글리프별 힌트는 **KS X 1001 한글 2,350자에만** 들어 있다 — 우리 글자 목록과 정확히 같은 범위다. ttfautohint 산물이 아니다(name 5 = makeotf).
- Pillow는 `ImageDraw.fontmode = "1"`이면 `FT_LOAD_TARGET_MONO`(1비트 전용 힌팅)로 그린다(Pillow 12.3.0 `_imagingft.c`). 별도 의존성(freetype-py)이 필요 없다 — freetype-py로 같은 모드를 돌린 결과와 2,000자 중 1,975자가 비트 단위로 같았다.

**측정(빈도 상위 2,000자, 세로 획 = 짧은 가로 런)** `[확인]`

| 자산 | 지금 방식 | 흑백 힌트 | 연결 성분 일치 |
|---|---|---|---|
| 20/400 | 1px 58.6% · 2px 35.6% | 1px 84.4% · 2px 10.5% | 86.5 → 88.2% |
| 20/700 | 2px 55.1% · 3px 37.4% | 2px 85.0% · 3px 9.1% | 64.8 → 70.1% |
| 28/700 | 3px 72.2% | 3px 81.6% | 85.0 → 82.4% |
| 16/400·칩 16/700 | 1px 69.9% / 2px 73.8% | 82.6% / 88.6% | 98.0 → 100% / 동일 |
| 32·62·78px/800 | 차이 ±5%p 안, 눈으로 구분 어려움 | | 100% 동일 |

- 폰트 자체 힌트가 FreeType 오토힌터보다 낫다(20px Regular 세로 획이 한 가지 굵기인 글자 27.0% vs 12.2%).
- **부수 발견 — 결함 수정**: 지금 방식의 `nanum16r`은 `↑`·`↓`가 화살표 머리 끝 4픽셀만 남고 몸통이 없었다(가는 몸통이 회색이라 128을 못 넘음). 흑백 힌트로 18픽셀이 된다. 회귀 테스트를 추가했다.
- 가로 획(세로 런)에는 효과가 작다(28px 67.0 → 67.3%). 획이 전체적으로 가늘어진다(20px Regular 글자당 잉크 80.6 → 73.3px) — 사용자가 원한 방향이다.

**결정**: 폰트 6종·이미지 14종 전부를 흑백 힌트로 다시 구웠다(`gen_fonts.py`·`gen_images.py` 각 한 줄, JSON 메타에 `raster: pillow-mono-hinted`). 폰트 614,829B·이미지 16,287B. 셀이 1px씩 바뀐 자산이 있다(예: 20/400 20×21 → 21×22). 렌더는 폰트마다 자기 베이스라인으로 정렬해 영향이 없다.

**⚠️ 팀 승인 필요** — 사용자(dh)가 측정을 보고 정한 것이고, 폰트 교체 논의가 아직 열려 있어 자산 PR에서 팀원 전체 승인을 받는다. 힌트로 풀리지 않는 것(폰트 교체 논의의 근거):
- 가로 획 굵기에는 힌트 효과가 약하다.
- 글리프 디자인 자체의 들쑥날쑥함(예: `특`이 `강`보다 아래로 길다)은 힌트로 고칠 수 없다.
- 16px `↑`·`↓`는 몸통이 살아났지만 폭 1px 막대 + 머리 3px라, 멀리서 `↑ 4개 더`가 `14개 더`로 읽힐 수 있다(렌더 PR 최종 리뷰 지적) — §7.
