## 3. 결정별 근거

### 3.1 D1 — 폰트 글자 집합: KS X 1001 2,350자

**쟁점 (2026-09-21, P2 서브셋을 전제로 정리, P1을 택하면 아래 2~5·7·9~11은 사라진다)**

1. **글자 집합을 어떻게 정하나** — e-fairboard 방식(코퍼스 빈도 상위 2,000자, 도메인 무관)과 사용자 제안(예상 과목·특강명 기반, 교수명·예약 문구는 예측 어려움)을 절충해 **KS X 1001 2,350자를 안전망으로, 실데이터를 하한선으로** 쓴다. 글자 하나 추가 비용은 **172B**(20px 60B + 28px 112B). `[계산]`
2. **화면 글자의 입력 경로가 3곳이다** `[확인]`: CSV 임포트(`server/app/domain/csv_import.py:117-120`)·REST 스키마(`server/app/schemas.py:59-70` `_bytes_max`)는 **UTF-8 바이트 길이만** 검증하고 글자 종류는 안 본다. 예약(`Reservation.subject/professor`)은 자유 입력이라 예측이 가장 어렵다. 글자 집합 검증을 넣을 지점은 CSV 임포트·REST 스키마 두 곳(wj 영역).
3. **집합 밖 글자 처리** — (가) 입력 거부 (나) 경고 후 저장 (다) 렌더 폴백(□/공백). 입력·오류 메시지는 wj·mh, 렌더 폴백은 dh.
4. **글자 집합의 단일 진실원** — 폰트 생성(dh)과 서버 검증(wj)이 같은 목록을 써야 한다. 위치 후보: `lora_proto/`(cw 전담·lockstep) / 펌웨어 쪽에 두고 서버가 복사(드리프트 위험) / 공용 자산 폴더. **cw 결정 필요 → D6.**
5. **갱신 경로** — 새 글자가 필요해지면 폰트 재생성 + 펌웨어 재배포가 필요하다. OTA 경로 유무 `[미검증]` — 그래서 초기 집합을 넉넉히 잡는 게 안전.
6. **집합 크기 N별 저장량**(한글 N자+ASCII 95자, 1비트) `[계산]`:
   - 2,000자: 20px 125,700B + 28px 234,640B = 360,340B
   - **2,350자(KS X 1001, 채택)**: 20px 146,700B + 28px 273,840B = 420,540B
   - 3,000자: 532,340B / 4,000자: 704,340B / 전체 11,172자: 1,937,924B
   - 실데이터 300자(아래 15) + ASCII·기호 100자: 68,800B — N 후보가 아니라 **반드시 포함해야 하는 하한선**
7. **저장 형식과 훅** — 커밋 훅이 500KB 초과 파일을 막는다. hex `.h`는 바이너리의 6.33배라 20px 4.28MB로 걸린다. **`.bin` 형식이면 420,540B로 훅을 그대로 통과**한다.
8. **글자 조회 방식** — 서브셋은 코드포인트→글리프 위치 조회(이진탐색/표)가 필요하다. 전체 한글의 산술 인덱스(`cp - 0xAC00 + 95`, v1 방식)보다 코드가 늘어난다.
9. **협의 순서** — wj(검증 추가), cw(단일 진실원 위치), mh(입력 오류 메시지). dh-04 마감(3주차)과 맞물려 자산 생성(Task 3) 전에 정해져야 한다.
10. **실데이터 확보 — 완료(2026-09-22)**. 글자 빈도 요약본 3종(과목명 233자·교수명 107자·한글 외 문자 33종)을 받아 분석. **범위 고지: 이 데이터는 정보통신공학과 학생 계정으로 접근 가능한 범위 안에서 얻은 최대치다. 다른 학과·전체 학사 범위를 대표하지 않는다.** 과목명의 22%(52/233자)·교수명의 15%(16/107자)가 표본에서 1회만 등장해, 범위를 넓히면 새 글자가 계속 나올 걸로 보인다 `[추정]` — 그래서 실데이터만으로 집합을 정하지 않고 KS X 1001을 안전망으로 썼다.
11. **커버리지 자동 검증(제안)** — 픽스처·CSV 표본의 모든 글자가 집합에 있는지 테스트로 확인할 수 있다. ⚠️ 승인 필요
12. **P1로의 후퇴 경로** — 생성 스크립트를 글자 집합 파라미터화해 두면 실데이터 조사 결과가 나쁘거나 플래시가 남으면 전체 한글로 재생성만 하면 된다.
13. **한글 외 문자도 집합에 필요하다** — 화면 스펙이 `·`(푸터)·`–`(강의시간)·`↑`/`↓`(목록)를 쓴다. v1 폰트 생성은 ASCII+한글 음절만 굽고 그 밖 문자는 안 그린다(`KoreanFont.h`의 `ngIdx`가 -1 반환). **실측(2026-09-22)**: 받은 한글 외 문자 33종(로마숫자·중점·하이픈·영문·숫자·괄호·전각 등)에 `–`·`↑`·`↓`는 **없었다** — 우리 UI가 그리는 기호라 학사 데이터엔 원래 안 나온다. 이 3개는 실데이터와 별도로 반드시 추가.
14. **실데이터 취급 — 완료(2026-09-22)**. 원본이 아니라 글자·코드포인트별 빈도 요약본 3개(CSV)를 받았다. 원본(교수 이름 등)은 저장소에 없고 수집한 쪽 로컬에만 있다.
15. **최종 글자 집합 분석(2026-09-22)** `[계산]`: 과목명 233자 + 교수명 107자(겹치는 56자 제외) = 284자. **놓칠 뻔한 것**: 상태 보조 문구·요일·layout 8 안내문 등 우리 쪽 고정 한글 UI 카피(폰트로 그려지는 것만, 라벨류 이미지는 제외)도 필요 — 서로 다른 55자 중 **16자(`끝납느늘단더되말않았없에요월입휴`)는 과목/교수 데이터에 없어서 284자만 썼으면 빠뜨렸을 것**. 최종 합집합 **300자**, 전부 KS X 1001·2,000자 빈도 목록 안. 표본 한계(10번)로 300자만 쓰는 건 위험 → **N = KS X 1001 2,350자**로 최종 확정.

**축 A(글자 범위) 선택지 비교**
- **전체 한글**: 누락 없음, 인덱스 산술이라 단순(v1 그대로). 단점: 크다(§5 P1 참조).
- **서브셋 2,000자(e-fairboard 방식)**: 0.36MB, 훅 통과. 단점: 목록 밖 글자 빈칸, wj 입력 검증 필요. 흔한 성씨·이름 약 130자(자체 표본) 전부 포함했으나 표본이 약함. KS X 1001 2,350자 중 359자가 목록에 없음(예: 잚·잦·짬).
- **KS X 1001 2,350자(채택)**: 실데이터 300자를 전부 포함하는 것을 실측 확인(15번). "희귀 글자 없음"을 가정이 아니라 근거로 말할 수 있는 유일한 안.
- **혼합(20px 전체+28px 서브셋)**: 교수명·과목명이 28px에만 나오는데 그 자리만 서브셋이면 위험이 가장 큰 곳에 몰린다. 기각.

**패키지 비교(참고, 전부 20px+28px 기준)**

| 패키지 | 글자 수 | 저장량 | 팀 간 의존 | 비고 |
|---|---|---|---|---|
| P1 전체 한글 | 11,172 | 1,937,924B(≈2.0MB, 앱 3MB의 66%) | cw(D2 훅 예외, D3 소유표) | 누락 위험 없음. 남는 1MB로 코드가 되는지 S7까지 `[미검증]` |

### 3.2 D2 — 저장소 반입: (d) 빌드타임 생성

D1이 P2'(420,540B)로 정해지며 `.bin` 자체가 이미 훅(500KB) 아래라, 애초 고려하던 (a) 훅 예외·(b) 500KB 분할·(c) Git LFS는 불필요해졌다. 남은 쟁점은 "이 `.bin`을 펌웨어 컴파일에 어떻게 넣느냐"였다.

**제약**: 로컬에 `espressif32` 플랫폼이 설치돼 있지 않다(`pio platform list` — `native @ 1.2.1`뿐, `[확인]`). `[env:terminal]`(실기)은 아직 없다. 실기 전용 메커니즘은 문서(`[출처]`)까지만 확인 가능하다.

1. **`board_build.embed_files`(PlatformIO 공식, espressif32 전용)** `[출처]` docs.platformio.org — objcopy로 `extern const uint8_t X_start[]/X_end[]` 심벌을 만든다. `embed_txtfiles`는 널 종단이 붙어 0x00 바이트가 실데이터인 폰트에 부적합 — `embed_files`를 써야 한다. **알려진 함정**: platform-espressif32 이슈#425, 일부 버전에서 링크 목록에 안 들어가는 버그 보고 `[출처]`. `native`에서는 이 옵션이 의미 없어(objcopy 기반은 espressif32/Arduino 전용) 로컬 실측 불가.
2. **(d) 빌드타임 생성 — 실측 완료** `[확인]`: `extra_scripts = pre:<script>.py`로 빌드 직전에 `.bin`을 읽어 `const uint8_t[]` 배열 `.cpp`/`.h`를 생성. 스파이크로 직접 검증(생성 후 삭제, `git status` clean·`pio test -e native` 31/31 회귀 없음 재확인):
   - `lib/<생성폴더>/`에 쓰면 LDF가 자동 링크(S3 plan Task 3의 "`lib/`는 자동 링크" 규칙과 동일). `build_src_filter` 수정 불필요.
   - 0x00 바이트가 안 잘리고 보존됨을 테스트로 확인(`SPIKE_FONT_DATA[5000..5003] == 0x00,0x00,0xff,0xff`).
   - 원본 `.bin`을 바꾸고 재빌드하면 즉시 갱신(스테일 캐시 없음, 5,004B→10B로 확인).
   - `pio check -e native`가 생성 파일도 스캔하지만 5KB 샘플 기준 새 지적 0건(Total 67 유지). 420KB 실제 규모의 소요시간은 `[미검증]`.
   - **실제 도입 시 필요**: 생성물이 `lib/` 밑에 생기므로 `.gitignore`에 추가해야 한다 — 안 하면 untracked로 잡혀 실수 커밋 위험(스파이크에서 실제로 잡히는 것 확인).
   - 호스트·실기 양쪽에 같은 메커니즘을 쓸 수 있어 보인다(`extra_scripts`는 플랫폼 무관 빌드 훅). 실기 쪽 실동작은 `[미검증]`.
3. **LittleFS 런타임 로드**: v2 스펙이 이미 `/schedule.bin` 등에 LittleFS 512KB를 쓰기로 했으니 폰트도 같은 파티션에 넣는 방안. 재조사 안 함(이전 판단 유지) — 마운트·읽기 코드 추가, 교체마다 별도 `uploadfs` 플래시가 필요해 (d)보다 무거움.

**결론**: (d). 로컬에서 실제로 동작을 확인한 유일한 방법이고, `embed_files`의 알려진 버그·실기 미설치 문제를 피하며, 호스트·실기 양쪽에 같은 메커니즘을 쓸 수 있다. 남는 미검증(실기 실동작, 420KB 규모 `pio check` 소요시간)은 `[env:terminal]`이 생기는 S7 근처에 재확인.

### 3.3 D3 — `renderLayout` 위치: B (`lib/render/`)

- **A `src/terminal/render.cpp`**: spec §4.1·소유 표와 일치. 그러나 `.cpp`가 `src/`에 있으면 `pio test`에 링크 안 됨(`undefined reference`) — 해결에 설정 3곳 수정 필요: `[env:native]`의 `test_build_src`+화이트리스트 `build_src_filter`, `native_preview` 필터, `check_src_filters`에 `+<src/>`. 세 수정 모두 실측, 기존 스위트 회귀 없음. `[확인]`
- **B `lib/render/`(채택)**: 설정 변경 0, `host_gfx`와 같은 검증된 구조, 게이트가 `lib/`를 이미 커버. 현재 `firmware/lib/`에는 `adafruit_gfx_vendor/`·`fixture_parse/`·`host_gfx/`·`lora_codec/`뿐이고 `render/`는 신설. `[확인]`(호스트) / 실기 `[env:terminal]`에서의 LDF 링크 `[미검증]`(espressif32 미설치).
- **B가 D2와 함께 동작하는지 실측(2026-09-23)**: `lib/render/`류 모듈이 `lib/font_data/`류의 다른 `lib/` 모듈을 `-I` 없이 `#include`해서 자동 링크되는지 스파이크로 확인 — **된다.** `[확인]` LDF가 lib 간 의존을 자동 해석한다.
- **폰트 헤더 include 중복 문제, 실측(2026-09-23)**: v1 방식대로 배열을 헤더에 직접 정의(`const uint8_t X[] = {...};` in `.h`)하면, include하는 `.cpp`마다 배열이 각각 지역 심벌(`nm` 출력 `r _ZL...`, 내부 링크)로 **실제 복제**된다. 링크 에러 없이 조용히 플래시를 두 배 이상 먹는다. `[확인]` **D2의 생성 방식(extern 선언은 `.h`에·정의는 생성된 `.cpp` 하나에만)은 이 문제를 구조적으로 피한다** — 정의가 한 곳뿐이라 몇 군데서 include하든 복제되지 않는다. 렌더 코드(B)는 반드시 D2가 만든 `extern` 헤더를 참조해야 하며, **폰트 배열을 헤더에 직접 정의하는 v1 원본 패턴을 그대로 복사해 오면 안 된다.**

**결론**: B. 다만 spec §4.1(`docs/specs/2026-09-16-s3-render-design.md:69`)과 파일 구조도는 여전히 `src/terminal/render.h/.cpp`를 명시하므로 **spec 자체 수정이 필요하다**(cw 영역, 소유 표 갱신과 함께 → D6).

### 3.4 D4 — 굵기 표현: 실제 Bold(700), 4-pass 기각

- **나눔고딕 Bold(700) 확보 가능**: Google Fonts에 Regular 400·Bold 700·ExtraBold 800 전부 공식 제공, 같은 오픈소스 라이선스. `[출처]` fonts.google.com/specimen/Nanum+Gothic, CSS2 API로 실제 TTF(2,071,704B) 다운로드해 확인. `[확인]`
- **정량 비교(2026-09-23, 실측)**: 화면 문구 4종(`캡스톤디자인`·`김교수`·`13:00 - 15:00`·`웹프로그래밍`)을 20px·28px에서 v1 방식(셀=명목크기, 글리프=0.9배)으로 렌더.
  - 잉크 밀도: 4-pass 24~25% vs Bold(700) 단일패스 18~20% — **4-pass가 실제 Bold보다 더 굵다.**
  - 가로 획 런 평균·표준편차: 4-pass 4.36~5.69px(표준편차 3.27~4.86) vs Bold 3.65~4.55px(표준편차 3.38~4.01) — **4-pass가 더 굵고 더 불균일**(대각선·모서리 과다 뭉침).
  - 눈으로 확인: 4-pass는 `스`·`인` 같은 곡선에서 획이 뭉개진 인상, Bold(700)는 획 굵기가 고르고 글자 구분이 더 선명.
- **v1식 4-pass는 기각.** "간단하니까 우선 쓰고 본다"는 최초 추천이 실측으로 뒤집혔다.
- **저장량 정정**: 화면 스펙 타입표(`terminal-epaper.md:72-77`)를 다시 대조하니 **28px는 스펙 전체에서 항상 weight 700 하나로만 쓰이고 28px Regular 용례는 없다** — Bold가 기존 28px 자리를 그대로 대체할 뿐이라 §3.1의 저장량은 **변경 없음**(28px 글리프를 Regular 대신 Bold로 굽는 것뿐, 벌수 추가 아님). 중간에 "추가 273,840B"라고 썼던 건 확인 없이 넘겨짚은 것이라 정정.
- CPU 비용은 측정하지 않았음(호스트 렌더 스크립트일 뿐 ESP32 실기 타이밍 아님) — Bold 채택으로 4-pass 반복 그리기 자체가 없어져 이 우려는 소멸.

**별개로 발견한 것(D4 범위 밖, 미결로 남김)**: 타입표는 20px·16px에 weight 500을 지정하는데, 나눔고딕은 400·700·800만 있고 **500(Medium)이 없다** `[확인]`. v1도 이 자리에 plain Regular(400)를 근사치로 썼다. 지금 결정할 사안은 아니지만 mh·cw에 알릴 만하다.

**결론**: 실제 Bold(700). 저장량 변화 없음.

### 3.5 D5 — 16px 한글(`호`·`개`·`더`): 폰트 글리프로 굽는다

이전(9/21) 제안은 "이미지로 뺀다"였다. 실측해보니 근거가 약해 뒤집었다.

- **범위 재확인**: `terminal-epaper.md:77,87,138` 대조 — 16px에서 폰트로 그려야 하는 한글은 **`호`(헤더, 호수 뒤)·`개`·`더`(오늘 목록 `↑/↓ n개 더`) 3글자뿐**. `[확인]` 푸터(`E · 301 · U1`)는 한글 없음, 목록 시각은 숫자뿐, 칩류(오늘·type 약어 4종·변경 배지)는 스펙이 이미 이미지로 확정(`:228`).
- **저장 비교**: v1 `LabelImages.h` 유사 크기 항목(150~280B, 1~2음절 라벨) 기준 역산하면 이미지(`호`+`개 더` 합성) 약 100B, 폰트 글리프 3개(16px 1비트) 약 96B — **거의 동일**. "이미지가 유리"라는 이전 근거는 재계산 결과 없었다.
- **legibility 실측**: 16px 나눔고딕으로 `호`·`개`·`더` 렌더 — 자모 수가 적어(2자모) 획 겹침 없이 또렷함. `[확인]`
- **결정적 차이는 저장이 아니라 구조**: (a) 폰트 글리프는 D2 생성 파이프라인에 크기 파라미터 하나(16px) 추가로 끝 — 거의 공짜. (b) 이미지도 별도 파이프라인이 필요하지만 어차피 칩류 때문에 만들어야 함 — 공짜에 가까움. (c) `n개 더`는 가변 자릿수 숫자 뒤에 고정 문구가 붙는 형태라, 이미지면 숫자 폭만큼 x좌표를 수동 계산해야 하고 폰트면 이어서 텍스트만 그리면 됨 — **폰트 쪽 코드가 더 단순**. (d) 폰트를 나중에 교체하면(픽셀 폰트 등) 글리프는 자동 갱신되지만 이미지는 재작업 필요.

**결론**: 폰트 글리프로 굽는다.
