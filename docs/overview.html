e-Paper + LoRa 저전력 강의실 시간표 게시 시스템 — 구상도와 실행 계획

이 문서는 팀원 넷이 같은 그림을 보기 위한 것입니다. 스펙 원본은 docs/specs/의 두 마크다운이고, 여기서는 그 내용을 요약·시각화하고 체크리스트로 바꿨습니다. 두 문서가 충돌하면 스펙이 이깁니다.

1한눈에 보기

문제. 강의실 문의 종이 시간표는 학기 중 휴강·보강·대관이 반영되지 않는다. 정보는 포털에만 있고, 학생이 서 있는 문 앞에는 없다.

해법. 배선 없이 문에 붙는 배터리 구동 e-Paper 단말이, 관리자가 웹에서 바꾼 내용을 LoRa로 받아 수업 중 / 쉬는 시간 / 휴강 / 빈 강의실 / 시험 중 / 특강 / 대여 중을 상시 표시한다. 서버가 죽어도 단말은 자기 시계·자기 데이터로 옳은 화면을 유지한다.

2시스템 구상도

메인Pi가 갖는 것 / 갖지 않는 것

갖는다: DB 원본, room_versions, outbox, terminal_status, pending_devices, modems(모뎀Pi 레지스트리)

갖지 않는다: 무선 파라미터 실행, TXN, 재시도, 프레임 바이트

모뎀Pi가 갖는 것 / 갖지 않는 것

갖는다: 로컬 jobs 큐(SQLite), 노드 목록(메인이 내려줌), codec, TXN·재시도·FIFO·단일 인플라이트·CAD

갖지 않는다: 시간표 원본, 버전 부여, 사용자

3데이터 흐름 — "웹에서 휴강 등록"이 화면에 닿기까지

#어디서무슨 일근거
1메인Pi 웹관리자가 휴강 등록 → api.enqueue_resv_set(...) 호출. 한 트랜잭션에서 room_versions[resv] +1(255→1 롤링) 하고 그 값을 NEW_VER로 outbox에 삽입 (state=queued). 호수의 유닛이 2개면 행 2개, 같은 NEW_VERv2 §8.3 · 로드맵 §4.5
2메인Pi 허브그 건물의 모뎀Pi가 연결되어 있으면 job 메시지 송신. 모뎀Pi가 job_accepted로 답하면 dispatched. dispatched는 재전송하지 않는다 → 중복 없음로드맵 §4.2
3모뎀Pi 링크job을 검증 없이 JobStore.put_job() → received로드맵 §4.3
4모뎀Pi 파이프라인pick_next(): priority(TIME 0 · RESV 1 · SLOT/EXAM/CMD 3 · FILE 5), 같은 노드에 sending 있으면 건너뜀. codec으로 프레임 조립, TXN 배정(노드별 1~255 롤링), modem.py로 {"op":"tx","frame":…,"wake":true,"ack_ms":3000}v2 §8.4 (모뎀Pi로 이관)
5모뎀 펌웨어CRC8 검증 → CAD(채널 비었나) → wake 프리앰블 3 s + 프레임 송신 → 3 s ACK 대기 → tx_done acked|no_ack|cad_busy|errorv2 §4.4
6ESP노드딥슬립 중 DIO1 웨이크 → 헤더 NET_ID·BLD·ROOM·UNIT 필터 → 같은 TXN이면 DUP ACK → 적용 후 자기 버전을 NEW_VER로. (new − old) mod 256 ≠ 1이면 적용은 하되 GAP ACK → 렌더 완료 후 ACK → 다음 변경 시각까지 재슬립v2 §3.4·§3.5·§6
7모뎀Pi 파이프라인ACK 매칭(NET_ID·TYPE=ACK·BLD/ROOM/UNIT/TXN) → acked. no_ack면 5 → 20 → 60 s 후 재시도, 3회 실패 → failed. BUSY면 5 s 후(시도 횟수 증가 없음)v2 §8.4
8모뎀Pi 링크 → 메인Pijob_result 업로드 → outbox.acked, terminal_status 갱신. GAP이면 메인이 RecordProvider로 레코드를 읽어 FILE 작업 생성(전체 재동기)로드맵 §4.2

갱신 지연 기준 (확정): 정상 수신 시 30 s 이내 / 재전송 포함 최대 90 s. 지연 = 허브(≤0.1 s) + 인터넷(≤1 s) + 큐 픽업(≤0.5 s) + 전송·프리앰블(awake 0.3 s, WOR 1~3 s) + e-Paper 리프레시 15~20 s ≈ 20~25 s. 재시도 한 번이면 30 s를 넘으므로 상한 90 s. 벤치 기준: 100회 중 95회 이상 30 s, 전부 90 s.

측정: 시작 = 웹 저장 응답(outbox.created_at), 끝 = 리프레시 완료 후 ACK(finished_at). 히스토그램을 대시보드에 노출해 심사 때 실측치로 보여준다.

시간 동기와 오프라인

  • 모뎀Pi가 매시 :00:05에 TIME 브로드캐스트(자기 NTP 시계). 하루 1회(03:00) REQUEST_STATUS 플래그 → 노드들이 0~300 s 랜덤 지연 후 STATUS 업링크.
  • 인터넷이 끊겨도 모뎀Pi는 로컬 큐를 계속 송신하고 TIME을 계속 낸다. 결과는 쌓아뒀다 재접속 시 몰아서 보고(hello.pending_results). 24 h 이상 끊기면 메인이 dispatched를 failed(modem_offline)로.
  • 노드는 25 h 이상 TIME을 못 받으면 STATUS에 CLOCK_STALE. 렌더는 계속한다(fail-operational).

프로비저닝(초기 설치)

  1. 미설정 노드 부팅 → HELLO(mac, fw, batt) 송신, 화면에 NEW-xxxx(MAC 하위 2 B) 표시
  2. 모뎀Pi → uplink → 메인 pending_devices(modem_id, mac)
  3. 관리자 웹에서 강의실·유닛 배정 → 그 모뎀Pi로 SET_ROOM job + config.nodes 갱신
  4. 노드가 MAC 일치 확인 후 정체성 저장, 이후 자기 주소 프레임만 처리
