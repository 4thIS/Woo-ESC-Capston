# 진행 로드맵 · 서브프로젝트 분해 · 영역 간 계약 — 설계 (spec)

- 생성일시: 2026-09-09
- 수정일시: 2026-09-09
- 상위 문서: `docs/specs/2026-09-09-lora-v2-wor-design.md` (v2 시스템 설계). 이 문서는 **그것을 언제·누가·어떤 순서로 만들지**를 정한다. 프로토콜·펌웨어·백엔드의 기술 내용은 상위 문서가 원본이며 여기서 반복하지 않는다.

## 0. 배경 · 위치

v2 설계 스펙은 단말·모뎀·백엔드·웹 네 서브시스템을 다루며 한 번에 구현할 크기가 아니다. 규율 뼈대(CLAUDE.md·CODEOWNERS·CI)는 갖춰졌고 코드는 아직 없다. 이 문서는 첫 코드를 쓰기 전에 다음을 확정한다.

1. 전체를 어떤 서브프로젝트로 쪼개고 어떤 순서로 가는가
2. 병행 개발이 성립하려면 4주차까지 어떤 인터페이스 계약을 못박아야 하는가
3. 하드웨어가 없는 첫 3주에 무엇을 만드는가
4. 각 마일스톤에서 무엇을 어떤 수치로 보여주는가

## 1. 목표 · 비목표

### 목표
- 경진대회(12주차)에 **웹 수정 → LoRa → e-Paper 갱신** 루프가 단말 2대·배터리 구동·절전 모드로 동작하고, 관리자 웹·학생 웹·분석 대시보드가 함께 전시된다.
- 중간점검(7~8주차)에 같은 루프가 단말 1대·깨어있는 모드로 시연된다.
- 하드웨어가 없는 2~4주차에 네 사람 모두가 실제 코드를 쓴다.
- 최종발표(15주차)에 전력 실측(§1.4 목표 대비)과 1주 소크 결과를 표로 제시한다.

### 비목표 (이번엔 안 함 / 후속)
- 재실 감지 센서 및 그에 기반한 실제 점유 측정 — 계획서에서 제외. "점유율"은 **시간표·예약 기반 배정률**과 단말 상태 변화 로그로 정의한다.
- 학사포털·LMS 직접 연동(크롤링/API). CSV 업로드가 유일한 입력 경로.
- Python 단말 시뮬레이터(접근법 C). 필요해지면 후속.
- 3D 케이스 설계 상세 — S9에서 다룸.

## 2. 접근법 — B: 가짜 하드웨어로 3주 병행 → 부품 도착 즉시 수직 슬라이스

검토한 세 접근 중 B를 택했다.

| 접근 | 요지 | 기각/채택 이유 |
|---|---|---|
| A. 스펙 §11 직렬 (P0→P8) | 부품 오면 SF 실측부터 순서대로 | 첫 3주가 비고 웹 팀이 7~8주차까지 대기. 중간점검에 코드만 남음 → 기각 |
| **B. 가짜 하드웨어 병행** | fake 모뎀 + 호스트 렌더 프리뷰를 첫 3주 산출물로. 부품 오면 S5·S6로 수직 슬라이스 | 3주가 안 비고, 세 마일스톤마다 보여줄 게 생기며, 추가 산출물이 스펙 §10.1이 요구한 테스트 인프라라 낭비 없음 → **채택** |
| C. 단말 시뮬레이터까지 | B + Python 단말 시뮬레이터로 완전 분리 | `determineLayout`·`nextChangeAt`를 두 벌 유지해 스펙 원칙 4("상수는 한 곳") 위반 위험. 10주에 감당할 투자 아님 → 기각 |

B의 대가는 **계약을 앞당겨 못박아야 한다**는 것이다(§4). 스펙 §3·§4·§8.6이 이미 대부분을 정의해 두어 감당 가능하다.

### 4.1 `RenderModel` (확정)

상태 판단(cw)이 채워서 렌더(dh)에 넘기는 유일한 데이터. 렌더는 이 구조체 밖의 것을 읽지 않는다(시계·저장소 접근 금지).

```c
typedef struct {
  uint8_t  layout;              // v2 §5.3 표의 1~8
  char     bld; uint16_t room; uint8_t unit;
  char     nowStr[6];           // "HH:MM" — 렌더가 시계를 직접 읽지 않음
  uint8_t  weekday;             // 1=월..7=일
  struct { char subj[21]; char prof[13];
           uint8_t sH,sM,eH,eM; uint8_t type; uint8_t flags; } prev, cur, next;
                                // flags bit0 = 존재함, bit1 = 변경 배지(휴강·보강·변경)
  uint8_t  nToday;
  struct { uint8_t sH,sM,eH,eM; char subj[21]; uint8_t type; } today[12];   // 하단 오늘 목록
  char     qrUrl[48];           // 학생웹 진입 URL. 비어 있으면 QR 생략
  uint16_t battMv; uint8_t battPct;
} RenderModel;                  // ≈ 600 B. RTC 캐시 4 KB 예산에 포함하지 않음(매 웨이크 재계산)
```

- 문자열 길이는 v2 §5.1 저장 버퍼(과목 20 B·교수 12 B)와 동일.
- `today[12]`는 09:00~21:00 1시간 단위 가정(§9 열린 결정).
- QR URL은 호스트가 노트북↔Pi로 바뀌므로 펌웨어 상수가 아니라 **서버가 배포**한다. 배포 수단(TIME 페이로드 확장 vs 별도 CMD)은 S6 spec에서 정한다.
- 픽스처: `firmware/test/fixtures/render/*.json` (1파일 = 1화면). Python 프리뷰와 C++ Unity 테스트가 같은 파일을 읽는다.

### 4.2 `lora_service` 소유 구조 (확정)

`server/lora_service/`는 wj의 `server/` 안에 있되 **cw가 소유**한다(CODEOWNERS 반영 완료). 한 프로세스·한 DB·한 배포라는 운영 모델과 v2 §8.3의 "outbox 삽입 + 버전 증가 = 한 트랜잭션" 원칙을 지키기 위해 패키지 분리·별도 프로세스는 택하지 않았다.

실무 규칙 (S2 spec과 `server/CLAUDE.md`에 반영):

| 상황 | 규칙 |
|---|---|
| 웹이 outbox에 넣고 싶을 때 | `api.enqueue_*`만 호출. `models.Outbox` 직접 INSERT 금지 |
| LoRa 계층이 시간표 레코드가 필요할 때 | `RecordProvider` 콜백만. 웹 ORM 모델 직접 import 금지 |
| `lora_service/` 외부 노출 | `api.py`와 `set_record_provider`만. 웹 코드는 그 밖의 모듈을 import하지 않는다 |
| `pyproject.toml` 변경 | PR 제목 `chore(server): deps`, wj·cw 모두 리뷰 |
| DB 마이그레이션 | `outbox`·`terminal_status`·`room_versions`·`pending_devices`·`lora_log`는 cw, 나머지는 wj. 파일명 prefix `lora_` / `web_` |

## 5. 하드웨어 없는 3주(2~4주차)의 산출물

### 5.1 fake 모뎀 (`server/lora_service/fake_modem.py`, S1)

v2 §4.2·4.3의 JSON lines 프로토콜을 그대로 말하는 Python 객체. `modem.py`는 실물 시리얼이든 fake든 같은 인터페이스(`tx()`, `rx` 스트림, `ping`)로 다룬다.

| 기능 | 동작 |
|---|---|
| 정상 | `tx` 프레임을 파싱해 지정 지연 후 `ACK(OK)`를 `rx`로 되돌림 |
| 시나리오 주입 | `fake.script([...])`로 순서 지정: `no_ack`, `GAP`, `BUSY`, `FILE_MISSING(seq)`, `cad_busy`, `DUP` |
| 가상 단말 상태 | (bld,room,unit)별 `schedVer/resvVer/examVer/lastTxn` 보유 → 스크립트 없이도 DUP·GAP을 실제 규칙대로 판정 |
| 로그 | 송수신 프레임 hex 기록 → `lora_log`와 대조 |

효과: S2 워커 테스트(v2 §10.1)가 하드웨어 없이 완성되고, 관리자 웹은 2주차부터 "저장 → outbox → acked"가 실제로 도는 서버를 상대로 개발한다.

### 5.2 렌더 프리뷰 (`firmware/tools/render_preview.py` + `[env:native]`, S3)

```
fixtures/render/layout1_class.json ─▶ [env:native] render → 800×480 3색 프레임버퍼 → PNG
```

- GxEPD2와 같은 `drawPixel/print` 인터페이스를 가진 **호스트용 프레임버퍼 클래스**를 둔다. 렌더 코드는 어느 쪽에 그리는지 모른다(렌더 → 그리기 인터페이스 ← 구현체).
- 픽스처: 8개 레이아웃 × 경계 케이스(긴 과목명, 오늘 강의 0개, 저전압 등) 약 15개.
- PNG를 PR에 첨부해 mh·wj가 화면 디자인을 리뷰한다.
- 같은 native env가 `determineLayout`·`nextChangeAt` Unity 테스트도 실행 → P1 CI가 켜진다.

### 6.1 갱신 지연 기준 (확정: "정상 30 s / 재전송 포함 90 s")

계획서의 "30초 이내 갱신"을 두 수치로 둔다. 근거: 지연 = 워커 폴링(≤ 0.5 s) + 전송·프리앰블(awake 0.3 s, WOR 1~3 s) + **e-Paper 3색 풀 리프레시(15~20 s, §9 열린 결정)** ≈ 20~25 s로 정상 경로는 30 s 안에 들어오지만, v2 §8.4 재시도(5·20·60 s) 한 번이면 넘는다. 재시도 간격을 줄이는 대안은 `BUSY`(렌더 중, 15 s 이상) 케이스와 충돌해 기각. 95 % 기준은 §10.2-2의 수신률 기준과 같은 숫자다.

측정 정의 (S6·S7 spec에 그대로 들어감):

| 항목 | 정의 |
|---|---|
| 시작점 | 관리자 웹 "저장" 응답 시각 = `outbox.created_at` |
| 끝점 | **e-Paper 리프레시가 끝난 시각.** 단말이 렌더 완료 후 ACK를 보내도록 S6에서 순서를 고정 → `outbox.acked_at − created_at`이 곧 갱신 지연 |
| 표본 | SLOT_SET·RESV_SET 각 50회, 단말 2대 교대, 게이트웨이와 같은 방·다른 층 각 절반 |
| 기록 | `lora_log.air_ms` + 위 차이. 히스토그램을 S8 대시보드 "단말 상태" 화면에 노출 — 심사 때 실측 데이터로 제시 |

계획서 5.2-1)·6.1의 문구는 "30초 이내(정상 수신 시)"로 보정한다.

## 9. 열린 결정 (해당 서브프로젝트 spec에서 확정)

- **하루 최대 교시**: `today[12]`는 09:00~21:00 1시간 단위 가정. 야간 강의가 더 있으면 S3 spec에서 늘린다.
- **7.5" 3색 패널 풀 리프레시 시간**: 15~20 s 가정. v1 실측값이 있으면 §6.1 근거를 그 값으로 교체.
- **QR URL 배포 수단**: TIME 페이로드 확장 vs 별도 CMD — S6 spec.
- **CSV 컬럼 규격**과 REST 엔드포인트 목록 — S2 spec.
- **부품 발주 확정일** — 확정되는 즉시 §5.3의 5주차 기점을 실제 도착일로 갱신.
